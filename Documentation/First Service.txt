# 5. Major Architecture Decision

Zenith is being developed as a **microservice/distributed system**.

The original application was more monolithic.

The architecture is now being changed so that major business domains become separate services.

The intended high-level architecture is:

```text
                         ┌─────────────────────┐
                         │    API Gateway      │
                         └──────────┬──────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              │                     │                     │
              ▼                     ▼                     ▼
      Market Data Service    Security Service      Other Services
              │                     │
              ▼                     ▼
       Market Data DB          Security DB
```

Future major services include:

```text
API Gateway
Market Data Service
Security Service
Indicator Service
Screening Service
Analysis Service
```

There may eventually be additional infrastructure/services for:

* messaging
* background jobs
* caching
* monitoring
* distributed processing

But these should not be introduced prematurely.

# 6. Microservice Principle

Each service should own its own business logic.

For example:

### Market Data Service

Responsible for market data.

### Security Service

Responsible for identifying securities and maintaining company/security metadata.

### Indicator Service

Responsible for calculating technical indicators.

### Screening Service

Responsible for screening and scoring securities.

### Analysis Service

Responsible for higher-level analysis, including future news, YouTube and LLM functionality.

A service should not directly import another service's internal classes.

For example, this should eventually be avoided:

```python
from services.market_data_service.app.repositories.market_data_repository import MarketDataRepository
```

inside the Indicator Service.

Instead, services should communicate through defined interfaces such as:

* HTTP APIs
* events
* queues
* jobs
* messaging
* other explicitly designed service contracts

The exact communication mechanism can evolve later.

The important rule is:

**Do not create direct internal dependencies between microservices.**

---

# 7. Service-Owned Database Principle

Each major microservice should own its data.

The Market Data Service owns its market-data database/schema.

The Security Service will eventually own its security metadata.

The Indicator Service may eventually own indicator-related data if persistent storage is needed.

Do not create one giant shared repository layer where every service directly accesses every other service's tables.

The database boundary is part of the microservice architecture.

# 16. Bulk Ingestor

Location:

```text
services/market_data_service/app/ingestion/bulk_ingestor.py
```

Purpose:

Coordinate provider retrieval and mapping.

Current conceptual implementation:

```python
class BulkIngestor:

    def __init__(self, provider, mapper):
        self.provider = provider
        self.mapper = mapper

    def fetch(self, symbols, period="5d", interval="1h"):
        if not symbols:
            raise ValueError("At least one symbol is required.")

        raw_data = self.provider.get_market_data(
            symbols=symbols,
            period=period,
            interval=interval,
        )

        return self.mapper.map_market_data(
            raw_data,
            interval,
        )
```

The important responsibility chain is:

```text
BulkIngestor
    ↓
Provider
    ↓
raw data
    ↓
Mapper
    ↓
normalized internal records
```

# 18. Market Data Processor

Location:

```text
services/market_data_service/app/processing/market_data_processor.py
```

Purpose:

Calculate reusable market-derived values before data is stored.

Current calculations include:

### Price

```text
price_change
price_change_percent
trading_range
```

### Volume

```text
average_volume
```

using a 20-period rolling average.

### Average price

```text
average_price
```

calculated from OHLC:

```text
(open + high + low + close) / 4
```

### Relative volume

```text
relative_volume
```

calculated as:

```text
volume / average_volume
```

### Buying pressure

Based on the close position inside the high-low range:

```text
(close - low) / (high - low)
```

### Selling pressure

```text
(high - close) / (high - low)
```

### Momentum

Current implementation uses a 10-period difference:

```text
close.diff(10)
```

### Volatility

Current implementation calculates rolling standard deviation of percentage price changes over 20 periods.

The processor sorts data by:

```text
symbol
datetime
```

before calculating these values.

This is important because rolling and difference calculations depend on chronological order.

The processor is intended to calculate market-data-derived values, not screening decisions.

Purpose:


Datetime is converted using pandas datetime conversion.

### Numeric normalization

Numeric fields are converted using numeric conversion.

Fields include:

```text

high
low
close
volume
price_change
price_change_percent
trading_range
average_volume
average_price
relative_volume
buying_pressure
selling_pressure
momentum
volatility
```

### Invalid-value handling

Positive and negative infinity are converted to missing values.

### Missing-value handling

Pandas missing values are converted into Python `None` where appropriate.

### Ordering

Final records are sorted by:

```text
symbol
datetime
```

The normalizer does not perform business decisions.

# 24. Critical Database Identity Decision

This is one of the most important architectural decisions.

A market-data record is uniquely identified by:

```text
symbol + datetime
```

NOT:

```text
symbol + datetime + interval
```

The interval is stored as a field, but it is not part of the unique identity.

Therefore:

```text
AAPL + 2026-09-25 10:30
```

represents one record.

If another request provides:

```text
AAPL + 2026-09-25 10:30 + 5h
```

the existing record should be updated rather than creating another row.

The interval field should then be updated as part of the upsert.

This decision was explicitly made because the same timestamp may be encountered through different interval requests.

Do not change this identity model unless the developer explicitly changes the requirement.

# 30. Important API Design Rule

The API route should not manually create:

```python
data["interval"] = interval
```

The interval should come from the mapper.

The Mapper creates the normalized record structure.

This keeps provider mapping responsible for the source-to-internal-data transformation.

# 44. Coding Style

Use readable Python.

Prefer:

```python
class MarketDataRepository:

    def __init__(self, session: Session):
        self.session = session
```

over unnecessary abstraction.

Functions should have clear responsibilities.

Small comments inside functions are preferred.

Comments should explain purpose, not obvious Python syntax.

Avoid excessive comments.

Avoid giant functions when responsibilities are genuinely different.

But also avoid splitting code into meaningless micro-files.

# 51. Final Architectural Summary

The core Zenith philosophy is:

```text
Each service owns a business domain.

Each service owns its internal implementation.

Each service owns its database when persistent data is required.

Services communicate through defined interfaces.

Services do not import each other's internal implementation.

Market Data owns market data.

Security owns security identity.

Indicator owns technical indicator logic.

Screening owns screening logic.

Analysis owns higher-level analysis.

API Gateway routes requests.

PostgreSQL stores persistent data.

Alembic manages service-owned schema migrations.

Yahoo currently provides external market data.

The system is designed for bulk processing and future scale.
```

The most important current database rule is:

```text
Market Data identity = symbol + datetime
```

not:

```text
symbol + datetime + interval
```

The most important current service-boundary rule is:

```text
Other services request Market Data through the Market Data Service.

They do not directly access the Market Data database.
```

The immediate next implementation task is:

```text
Market Data Service
    ↓
Database retrieval
    ↓
Retrieval API
    ↓
Tests
```

After that, development can move to the next microservice.
